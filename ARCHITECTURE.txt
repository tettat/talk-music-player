====================================

Desktop lifecycle
-----------------
One Electron main instance -> one owned Python stdin pipe -> random localhost port.
Readiness is received only through the child's pipe, then checked by health identity.
Last window closes -> stdin shutdown -> server exit -> Windows job kills descendants.
If Electron crashes, pipe EOF still shuts down the backend. If backend crashes, the
OS closes its private job handle and terminates remaining model children.
No Node integration in renderer. The sandboxed preload exposes only fixed window
actions and sanitized window state, never generic IPC, filesystem, shell or accounts.
Main-process handlers verify the owning webContents, main frame, URL and origin.
Context isolation, sandbox and web security stay enabled. No popup, webview,
arbitrary permission or remote navigation.
Music/lyrics/cover network access happens in the bounded provider backend only.

The frameless window keeps three custom controls in the existing search row. Global
viewport positioning and drawer head clearance prevent panels covering the controls.
When an HTML modal opens, the one control group is reparented into that top-layer
dialog: z-index alone cannot escape the modal's inert background. No desktop bridge
means hidden controls and unchanged browser/mobile layout. Maximize/restore follows
native window events, including OS-driven changes, rather than a guessed UI flag.

The legacy browser launcher remains a separate compatibility mode with TTL. The
desktop must never kill an unrelated listener or steal another app's process.

Local state / portability
-------------------------
Code paths use project-root-relative defaults, never a fixed username/drive.
config.local.json selects a user's optional external runtime and existing protected
authorization directory. Relative paths resolve against checkout even from other cwd.
No secret is stored in example config. Credentials, databases, audio, model binaries,
logs, experiments and screenshots are excluded from git.
DPAPI credentials intentionally cannot travel to another user/device: reauthorize there.
Current platform support: Windows x64, Python 3.12, Node 22+. Other OS credential
backends and packaged relocatable Python runtimes are future work, not guaranteed.

Dual-source implementation
--------------------------
Canonical identities are qq:<MID> and netease:<numeric song ID>. A bare legacy QQ
MID is only an input alias, never a newly stored key. First startup takes a consistent
SQLite backup before upgrading tracks, all foreign-key refs, queue/current state and
insight JSON keys in one deferred-constraint transaction. Listening seconds, timestamps,
playlist ordering and IDs are preserved. Conflicts/errors roll back instead of dropping
data or starting an empty library. Migration and rollback are tested with legacy fixtures.
Live validation uses a read-only clone, not the currently running user's DB.

QQ's credential, transport, source resolution and validated cache code remain unchanged.
The original qq network lock and account APIs remain compatible. NetEase has its own lock,
cache and errors. QQ reauthorization revokes QQ media grants only and cannot clear a
NetEase grant or stop an already playing NetEase stream.

The new renderer requests source slices independently, renders each as it arrives,
interleaves catalog ranks, preserves successful results/cursors through partial failure,
and retries only the failed source. Source filtering never changes a stored recording.
Grouping requires normalized title + complete artist set + album + duration within
2 seconds, excluding version/cover/live/remix annotations. UI groups are transient:
actual play/favorite/playlist/listening operations always use a concrete provider key.
Source clicks select future actions, not immediate playback; no automatic fallback.

NetEase uses normal first-party public free-source requests, not an identity claim or a
fallback from a failed QQ session. It checks exact recording details and current source
availability on every play, rejects trial/paid/protected/short sources, restricts verified
HTTPS CDN hosts, and scans/fully decodes MP3 before issuing opaque loopback media tokens.
Only the existing ordinary-MP3 validation functions are reused from QQ's local helper;
no QQ network or credentials are involved in NetEase requests. No NetEase GUI/DLL/cache
or upstream unblock package is used. Artwork uses bounded first-party proxy/cache routes.

Listening records persist source separately; totals/rankings/history share source filters,
and the UI's source share is based on listening time. Lyrics and analysis caches use the
same source-qualified key. API capabilities declare NetEase free-only, not login.

The renderer checks /api/features before enabling aggregation. If an older running backend
serves new static files, it retains compatible QQ-only searches until deliberate restart;
no automatic shutdown or live migration of that old process's database.

Still pending
-------------
The user prioritizes non-VIP free playback. NetEase QR authorization, protected session
persistence/refresh and member-full-source validation are deferred until actually needed;
they are not the next milestone. No QQ membership transfer is assumed. More providers
need their own adapters, credentials/capabilities and exact-source tests. Cross-device sync
is separate: derived personal records first; credentials/audio are not silently synced.

Windows private-test installer
------------------------------
NSIS x64 current-user installer now exists. Explicit positive source inventory,
official relocatable embedded CPython and hash-locked backend wheels; not a copied
venv. Packaged-only bootstrap resolves runtime files under resources and user state
outside them. No account/music/database/cache from the build machine is shipped.
Normal-close and owned-UI-crash lifecycle were tested from Chinese/space paths.
Clean Windows VM, wizard/uninstall/upgrade/rollback, signing, dependency/security
and public-license review remain release work; this is not a cleared public release.

Optional score capability
-------------------------
src/score_extension.py mounts a same-origin capability with its own persistent data,
one active worker/three waiting, cancel/retry, serialized immutable edit transactions,
Windows owned Jobs and disabled/lazy startup. No torch is imported into the host.
Host grants only library identities or bounded local uploads; authorized source is
copied before inference, without play/state/history changes. The standalone demo
remains independently runnable with a separate directory/lock.
Native chooser verifies a separately relocatable model/runtime/piano capability pack.
No generic renderer filesystem or shell API; no broad localhost/CORS allowlist.
ABC pitch-only correction preserves every part/rhythm/tie; save emits a pinned
revision's ABC/MusicXML/MIDI/FluidR3 media. Drafts cannot use stale playback/exports.
Original inference stays untouched. See capabilities/score_lab/INTEGRATION.txt,
EDITING.txt and PACK.txt. A general third-party plugin loader/QScore integration
is deliberately not implemented. Future learning capabilities can use separate
capability directories and narrowly scoped host grants.

Transcription research
----------------------
Production Basic Pitch integration is included. The YourMT3/ROSVOT/Transkun/Beat This
experiments and raw licensed-song outputs remain local research, not current player
features or audited distributable model packages. Their consolidation and score
previews are in the existing Feishu research document. Promotion requires per-model
runtime manifests, weight-license review, reproducible setup and separate UI/job work.
