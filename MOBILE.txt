talk 手机端可行性（2026-10-12，调研结论，非已实现功能）
====================================================

结论
----
值得做手机独立播放器，优先验证授权接口路线，不依赖完整 QQ 音乐 APP 常驻。
不能把“当前 Windows 已成功”当成 Android/iOS 会员播放已经验证。
桌面成品目前使用独立扫码授权、固定 QQ SDK 和本人授权的普通 MP3，
并非直接抽取官方客户端 DLL。应复用业务协议和 Provider，不搬 Windows EXE/DLL。

“类似方式”需要分开理解
----------------------
1. 自己的客户端登录、搜索、获取本人获准的音源、独立播放：有明确工程路线，
   但手机上的登录入口、续期、服务端授权与曲目可用性必须真机实测。
2. 不登录自己的客户端，直接复用手机 QQ 音乐已经保存的私有登录态：不能默认做到。
   Android 按 UID/进程/SELinux 隔离应用，原生 .so 同样受隔离；iOS 应用也有独立容器。
   只有对方明确提供的 SDK、导出组件、系统授权或共享接口才构成正常的跨应用通道。
3. 分析手机安装包里的模块：Android 可以另行做静态依赖/导出组件分析，
   但有 .so 不等于存在独立播放 SDK，也不等于获得另一应用的账号和服务端权限。
   当前未取得用户手机系统、客户端版本或安装包，没有做过对应动态验证。
   不将 root/越狱、私有凭据提取、注入或 DRM 绕过作为产品前提。

推荐验证顺序：先最小闭环，再完整 APP
----------------------------------
A. 在目标手机上验证本人独立授权：同机登录入口/回调、失败与取消、过期及续期。
   当前桌面的 QQ 二维码流程不能直接假设适合“只有一台手机”的使用场景。
   首先验证合法的系统浏览器/平台授权跳转；必要时先用另一设备显示二维码做 PoC。
B. 搜索指定歌曲并核对准确录音 ID、歌手和时长；验证一首会员歌和一首普通歌的
   实际播放权限、普通音频是否可解码与可拖动。拒绝权限时明确失败，不换试听/翻唱。
C. 验证音源过期、断网重试、登录失效，确认退出官方 QQ 音乐后仍可正常工作。
   若平台要求专属客户端/设备授权，需要重新评估，不能用绕过授权补齐。
D. Android 用自己的 Media3 Player/MediaSessionService，验证后台、锁屏、耳机、
   音频焦点/来电、暂停续播。iOS 独立实现 AVFoundation 播放与系统后台音频能力。
   移动端“退到后台仍听歌”与桌面“关最后窗口退出”是不同生命周期，不照搬 Electron。
E. 接入收藏、混合队列、歌词和本地听歌统计；复用统计口径，不把系统暂停/缓冲算入。
   最后做跨端资料同步与冲突处理，凭据和版权音频不自动同步。

需要替换的桌面组件
------------------
- Electron：移动端独立壳/原生播放器，不宣称现有 Electron 项目可以直接打成手机 APP。
- DPAPI：Android Keystore / iOS Keychain 对应的设备安全存储，在手机重新授权。
- Python 3.12 Windows wheel 锁、Windows Job Object：不直接拷贝到 ARM 手机。
- loopback 后端：迁移 Provider 请求逻辑到手机或受控的个人网关；现有服务是
  127.0.0.1-only、面向可信本机，不具备远程账号认证，不直接改为 0.0.0.0 暴露端口。
- 模型分析：手机端先不捆绑完整研究环境，另外评估 CPU、体积、电量与模型许可。

两个部署选择
------------
首选：手机独立授权、独立播放，电脑关机也能用；实现量较大，先做 A/B/C 验证。
临时：手机连接自己的受控电脑/网关，复用已验证 Provider；需要显式配对认证、TLS、
访问范围和限额，电脑/网关必须在线。这不是“手机已经独立接入”，当前没有实现。
